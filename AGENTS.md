# Writing articles for pdac.dev

## Voice

- Write in clear, direct English with British spelling.
- Use first-person singular when expressing the author's experience, judgement or proposal. Do not use institutional "we" by default.
- Be concise, engineering-led and concrete.
- Allow a sharp or provocative sentence when it exposes a real problem. Do not use marketing hype.
- Prefer short paragraphs, strong headings, examples, commands, diagrams and evidence.
- Avoid generic AI language, inflated claims, empty thought leadership and SEO keyword stuffing.
- Do not use em dashes.

## PDaC terminology

- Use **PDaC**, not **PDAC**.
- Spell out **Product Definition as Code (PDaC)** on first use in an article.
- Product Definition as Code is the methodology.
- ProductShape is the reference implementation.
- `pdac-lint` is an independent validator.
- Do not describe PDaC as a proven industry standard.
- Explain unfamiliar terms instead of assuming that readers accept project jargon.
- State limitations and uncertainty directly.
- Link to primary evidence in the specification and repositories.

## Article structure

- Open with the problem, not with PDaC's branding.
- Prefer one concrete example over several abstract claims.
- Separate product intent from delivery work, implementation and verification.
- Do not claim that structural validation proves that a product decision is true.
- Do not claim that PDaC guarantees implementation correctness or AI discoverability.
- End with a useful next step, concrete question or invitation to critical review when appropriate.

Articles are authored by Juan G. Carmona unless an issue says otherwise. The source in this repository is canonical. DEV.to versions, if published later, must be adapted or point back to the canonical pdac.dev article.
