## One rule, three wordings

Run this on any repository that has been doing Spec-Driven Development for a few weeks:

```console
$ grep -rn -i "refund" openspec/specs
billing/spec.md:4:  Refunds are issued for purchases made in the last 30 days.
checkout/spec.md:4: Customers can request a refund within 30 days of delivery.
support/spec.md:4:  If the order is less than a month old, offer a refund.
```

The same rule appears in three specs with three wordings and two meanings: 30 days from *purchase* is not 30 days from *delivery*. Nobody decided that fork. A coding agent paraphrased it into existence, and no human caught it, because specs are words only agents read. PDaC applies the oldest rule in engineering: don't repeat yourself.

**Define the rule once.** One small versioned file with an ID, in one agreed place:

```markdown
---
id: BR-REFUND-001
type: business-rule
title: Refund window
status: active
---

## Rule

Refunds are accepted within 30 days of delivery.
```

Every spec, ticket and prompt then points at `BR-REFUND-001` instead of restating it. Nothing is left to fork: the rule has one home, and the specs get shorter. No tool is needed to get this far, and [one rule is a fair place to start](/adoption/).

## Define, derive, build, verify, evolve

Defining one rule is the smallest slice of a longer loop. Product intent goes in once; work, context and expected behaviour come out; what delivery learns comes back as a proposed change. Anything marked next below is open backlog, not shipped product.

## Three doors, not three floors

**Write it down.** Structured product Markdown with stable IDs helps an agent before any tool is installed. **Agree how it changes.** The PDaC contract adds typed relationships and explicit Product Changes, approved by a person. **Make it checkable.** ProductShape verifies structure, links and citations deterministically. Enter through whichever door matches the failure in front of you: they combine in any order, and none removes human product judgement.

## What PDaC is, and where it stops

{/* Canonical PDaC definition, one-line and paragraph, verbatim from the spec
    repository's README (canonical-pdac-definition markers). Do not paraphrase
    or edit here. */}

Product Definition as Code keeps the agreed product definition in versioned Markdown that delivery work cites instead of restating.

The definition lives in small, related Markdown files: actors, journeys, use cases, business rules, domain terms and requirements. Together they form a validated product graph that humans and AI agents can read alike. It changes only through an explicit Product Change, reviewed and accepted by a human. Consumer documents such as SDD specs, tasks and agent prompts cite the exact product text they rely on by stable ID and content digest. When cited text changes, tools flag every recorded citation for review, so documentation drift is detected instead of remaining silent. Deterministic tools check structure and references, never truth. People decide what is true and what should change.

In practice the citation is the trust boundary between product and delivery: it records which exact product meaning a document relied on, and it makes that reliance checkable over time.

And there PDaC stops. Spec-Driven Development tools own one implementation increment; PDaC owns accepted product intent, the graph that outlives every spec. Delivery owns its implementation choices within that intent, and what it learns flows back as evidence and proposed Product Changes. One-way authority, two-way learning. The citation contract at the boundary is delivery-neutral: the same citations brief an SDD framework, an AI coding agent, or a human team working from the backlog.

## See the checks run (3 minutes)

Pointing a spec at `BR-REFUND-001` already stops the fork. Making that dependency checkable by a machine is a further step: each delivery document records the exact version of the rule it relied on, so one command can report when the rule moved underneath it. Teams tend to reach this once the definition itself has settled, rather than in week one. Here is what it looks like when they do.

The recording below tells one story from beginning to end:

1. **Act 1: the rule is restated.** Three specs describe the same refund rule in three different ways. Nobody chose the differences.
2. **Act 2: the rule is defined once.** Each spec replaces its copy with a citation carrying the rule's stable ID and content digest.
3. **Act 3: the rule changes.** `prodshape citations verify` flags every recorded citation that now needs a person to review it.

The recording is real output, not an animation: its end card names the exact CLI version it captured, and the same story is runnable below.

- **pdac-conformance** is the neutral conformance runner, versioned separately from the spec, that runs the published conformance tests against an implementation.
- **`@prodshape/cli`**: [![npm version](https://img.shields.io/npm/v/@prodshape/cli)](https://www.npmjs.com/package/@prodshape/cli)
- **v0.2.0 request for comments**: the released draft is open for comment on [GitHub Discussions](https://github.com/product-definition-as-code/spec/discussions?utm_source=pdac.dev&utm_medium=site&utm_campaign=rfc-comment).

**1. Every spec cites the rule instead of restating it.** `prodshape cite` emits the reference, carrying a content digest of the rule at the moment it was cited:

```markdown
## Returns
Refunds follow BR-REFUND-001. {pdac:cite id="BR-REFUND-001" digest="sha256:b5c58067…"}
```

**2. The rule changes.** In this sandbox, that means editing the file directly. A governed repository moves the accepted definition only through a Product Change. This demo skips that on purpose to trigger drift quickly, and the catch works the same either way. One command flags every citing spec by file and line. No grep needed:

```console
$ prodshape citations verify
stale  BR-REFUND-001  openspec/specs/billing/spec.md:4
stale  BR-REFUND-001  openspec/specs/checkout/spec.md:4
stale  BR-REFUND-001  openspec/specs/support/spec.md:4
warning PRODUCT061 openspec/specs/billing/spec.md [BR-REFUND-001]: Citation of 'BR-REFUND-001' is stale: canonical content changed since the citation was recorded
3 citation(s): 0 current, 3 stale, 0 tampered, 0 unresolved
```

Put that command in CI and stale product knowledge stops being invisible. PDaC does not rewrite the specs for you: a human reviews each flagged reference and updates the citation. `citations verify` reports one of four states for every citation:

- `current` - the cited text is unchanged.
- `stale` - the cited text changed since the citation was recorded.
- `tampered` - an embedded copy of the text no longer matches the original.
- `unresolved` - the cited artifact or anchor cannot be found.

**3. The whole script.** Verified against `@prodshape/cli@%PRODSHAPE_VERSION%` and served at [pdac.dev/demo.sh](/demo.sh). It shows the fork, the fix and the catch. This is a **non-governed sandbox**. It runs in a temporary directory via `npx`, with no global install and no git. You can run it again whenever you like.

<details>
<summary>The whole demo, copy-paste (3 minutes)</summary>

```bash
cd "$(mktemp -d)"
npm init -y >/dev/null 2>&1
npm install --save-dev --save-exact @prodshape/cli@%PRODSHAPE_VERSION%
prodshape() { npx --no-install prodshape "$@"; }

mkdir -p docs/product/model/business-rules openspec/specs/checkout openspec/specs/billing openspec/specs/support

# ACT 1: the same rule, restated by agents in three specs, three wordings
cat > openspec/specs/checkout/spec.md <<'EOF'
# Checkout

## Returns
Customers can request a refund within 30 days of delivery.
EOF
cat > openspec/specs/billing/spec.md <<'EOF'
# Billing

## Credits
Refunds are issued for purchases made in the last 30 days.
EOF
cat > openspec/specs/support/spec.md <<'EOF'
# Support playbook

## Refunds
If the order is less than a month old, offer a refund.
EOF

grep -rn -i "refund" openspec/specs
# purchase vs delivery vs "a month": nobody decided that fork

# ACT 2: define once, cite everywhere
cat > docs/product/model/business-rules/br-refund-001.md <<'EOF'
---
id: BR-REFUND-001
type: business-rule
title: Refund window
status: active
---

## Rule

Refunds are accepted within 30 days of delivery.

## Rationale

Customers need a predictable window; finance needs a bounded liability.

## Examples

A delivery on March 1 may be refunded through March 31.

## Exceptions

None.
EOF

CITE=$(prodshape cite --id BR-REFUND-001 \
  --file docs/product/model/business-rules/br-refund-001.md --form inline)

cat > openspec/specs/checkout/spec.md <<EOF
# Checkout

## Returns
Refunds follow BR-REFUND-001. $CITE
EOF
cat > openspec/specs/billing/spec.md <<EOF
# Billing

## Credits
Refund eligibility is BR-REFUND-001. $CITE
EOF
cat > openspec/specs/support/spec.md <<EOF
# Support playbook

## Refunds
Apply BR-REFUND-001 as written. $CITE
EOF

prodshape citations verify
# current x3: every spec agrees with the rule

# ACT 3: the rule changes (sandbox shortcut: a direct edit; a governed repository uses a Product Change)
node --input-type=module -e "
  import { readFileSync, writeFileSync } from 'node:fs';
  const p = 'docs/product/model/business-rules/br-refund-001.md';
  writeFileSync(p, readFileSync(p,'utf8').replace('30 days','14 days'));
"

prodshape citations verify
# stale x3: every citing spec, file:line. No grep.
```

On Windows, run it in Git Bash or WSL; the heredocs above are POSIX-shell constructs.

## Where this stands today

The specification is v0.2.0, released for public comment on 2026-08-28. The current ProductShape release implements it. Its [pinned conformance workflow](https://github.com/juangcarmona/productshape/actions/workflows/pdac-conformance.yml) passes all 44 published cases and verifies all 12 pinned digests. The file format remains `v1alpha1`, so existing product definitions do not need a migration. New v0.2 features, including Structured Behaviour, are optional and can be adopted through Product Changes. Next in the open backlog: deterministic projection of Structured Behaviour into test syntax, a packaged selection-to-briefing step, and coverage reporting between requirements, behaviours and tests.

The specification is still an early draft extracted from one working reference implementation. A second, independent implementation and external pilots are the next proof points. They are release gates for v1, not assumed achievements. The [known limits](/known-limits/) page names every gap we know about. The full list of specification changes is in the [v0.2.0 release notes](https://github.com/product-definition-as-code/spec/releases/tag/v0.2.0).
